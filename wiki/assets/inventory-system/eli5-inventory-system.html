장면 3 · 요구사항 분류

해야 할 일, 잘해야 할 일, 절대 깨지면 안 될 일

세 바구니에 나누면 기능/비기능 요구사항이 저절로 보여요.

🧩 기능 = 동사

  • 재고를 조회한다
  • 주문 수량을 예약한다
  • 결제하면 확정한다
  • 취소·만료 시 반환한다
  • 입고·반품을 반영한다

⚡ 비기능 = 정도

  • 조회가 매우 빠르다
  • 수백만 SKU를 다룬다
  • 동시 주문을 처리한다
  • 부분 장애에도 복구한다
  • hot SKU를 격리한다

🔒 불변식 = 약속

  • ATP는 음수가 아니다
  • 한 요청은 한 번만 차감
  • DB 커밋 전 성공 응답 금지
  • 확정·취소 중 하나만 성공
  • 변경 원인을 추적한다

기능은 박스가 되고, 비기능은 박스의 크기·복제가 되고, 불변식은 쓰기 경로가 돼요.

어른 버전: functional requirement는 API와 state transition으로, non-functional requirement는 topology·capacity·SLO로, invariant는 transaction boundary와 constraint로 변환한다.
장면 4 · 재고의 뜻

창고에 10개 있어도 10개를 다 팔 수는 없어요

이미 찜한 것과 비상용으로 남긴 것은 빼야 해요.

ATP = on_hand − reserved − safety_stock ≥ 0

이 식을 절대 깨지 않게 만드는 곳이 재고 시스템의 심장이에요.

어른 버전: Product가 아니라 SKU가 차감 단위다. command path의 첫 책임은 ATP >= requested_quantity를 하나의 원자적 연산으로 보장하는 것이다.

장면 12 · 완성 그림

이제 다섯 겹을 한 장에 합쳐요

읽기, 정확한 쓰기, 이벤트, 복구, 확장을 색으로 나눠 말하면 끝!

읽기정확한 쓰기이벤트복구·확장
  1. 조회 — 사용자가 Query API에 “재고 있어요?”를 묻는다. 주문과 완전히 분리된 읽기 전용 길
  2. GET — Query API가 Redis projection {atp, status, version}을 읽는다. miss·장애 시에는 rate limit을 걸고 DB read로 제한 fallback
  3. 주문 — 사용자가 Order Service에 주문을 넣는다. 화면에서 본 재고 숫자는 참고일 뿐, 여기서는 아무것도 판정하지 않는다
  4. reserve / confirm / release — Order Service가 예약·확정·취소 세 전이를 같은 문지기에게 요청한다. order_id + sku_id가 멱등키라 재시도해도 한 번만 차감되고, 확정·취소는 WHERE status='RESERVED' 조건부 전이라 둘 중 하나만 성공
  5. 조건부 UPDATE — Inventory Command가 WHERE ATP ≥ qty로 예약을 시도한다. affected rows=1만 성공이고, reservation·movement·outbox를 같은 트랜잭션에 커밋한 뒤에만 성공 응답
  6. RECEIVE / ADJUST — 입고·반품·관리자 조정도 같은 Inventory Command를 통과해 같은 원장에 movement로 남는다. 공급 측이라고 DB를 직접 고치지 않는다
  7. outbox — 커밋된 outbox 행을 relay가 꺼내 Event Bus에 발행한다. DB에 없는 변경은 나가지 않고, 커밋된 변경은 반드시 나간다 (at-least-once)
  8. consume — Projection Updater가 이벤트를 소비한다. 같은 편지가 두 번 와도 무해하도록 설계
  9. version 갱신 — Redis에 저장된 version보다 큰 이벤트만 반영한다. 순서가 뒤바뀌거나 중복돼도 전광판이 과거로 돌아가지 않는다
  10. 만료 반환·대사 — Worker가 만료된 예약을 DB 상태 전이로 반환하고, balance↔reservation↔movement 장부를 맞춰본다. 차이는 덮어쓰지 않고 보상 movement로 기록
  11. Redis 재구축 — Worker가 DB 기준으로 projection을 다시 만들라고 Projection Updater에 시킨다. Redis 장애·유실 뒤 돌아오는 길
  12. 확장 레인 — 측정된 병목에만 연다. hot SKU는 durable queue + single writer나 quota, 멀티 창고는 물류센터(FC, fulfillment center)마다 재고를 따로 세는 (sku, fc) 풀과 어느 센터에서 출고할지 고르는 할당 단계, 한 행의 한계를 넘으면 파티션별 이벤트 원장. 일반 SKU는 sku_id shard로 충분
  1. 초록색으로 사용자 → Command → DB를 그리고 조건부 예약을 쓴다. 입고·조정(WMS)도 같은 Command로 들어오게 잇는다.
  2. 파란색으로 Query → Redis를 추가하고 cache miss만 DB에 잇는다.
  3. 보라색으로 DB Outbox → Event Bus → Redis/UI 갱신을 잇는다.
  4. 주황색 점선으로 만료·대사·재구축이라는 돌아오는 길을 그린다.
  5. 마지막에만 확장 레인 박스를 가리킨다. hot SKU·FC 할당·파티션 원장은 꼬리 질문이 올 때 말로 푼다.

백지에서 이 순서로 세 번 그리면, 완성 그림을 외우지 않아도 다시 만들 수 있어요.

면접 답변 순서: 요구사항 질문 → 불변식 → 최소 write path → read cache → outbox/eventual consistency → 장애와 대사 → 측정된 병목의 확장. 각 화살표에는 기술 이름보다 무슨 동작을 하고 어떤 보장을 주는지를 적는다.
장면 13 · 대안 그림

전광판이 심판까지 맡으면 어떻게 될까

국내 커머스에서 실제 운영된 구조. 부품은 장면 12와 같지만 화살표 방향이 반대예요.

Redis 판정이벤트DB 반영·적재롤백
  1. PUT 차감·회수 — 주문이면 차감, 취소면 회수를 같은 API로 요청한다. 일반·직매입·추가구성·지점 상품을 각각 차감
  2. Lua 검사+차감 — 재고 서버가 Redis에서 한정수량 딜 풀을 먼저, 없으면 상품 풀을 검사한다. 남으면 판매수량 +a·재고수량 −a, 부족하면 에러. 여기서 판매가 결정된다
  3. 차감 성공 시 발행 — Redis 차감이 끝난 뒤에만 Kafka에 이벤트를 보낸다. key가 재고번호라 같은 재고는 한 파티션에서 순서대로 처리
  4. consume — 동기화 서버가 파티션 수만큼 붙어 이벤트를 읽는다
  5. UPDATE ±a — 재고 부족 검사는 이미 Redis가 했으므로 조건 없이 UPDATE만 한다. 재고가 0이면 품절 상태 코드로 바꾼다
  6. 최초 miss 적재 — Redis에 키가 없을 때만 DB에서 읽어 올린다. 평소 DB는 읽히지 않아 부하가 낮다
  7. 롤백 — 결제 오류 콜백이 오면 트랜잭션 ID로 회수 API를 불러 Redis에 되돌리고, 같은 경로로 DB에도 반영된다
  • A ② 차감 뒤 ③ 발행 전에 재고 서버가 죽으면 Redis만 줄고 DB는 그대로다. 두 저장소를 한 트랜잭션으로 묶는 장치(outbox)가 없다
  • B 복제가 비동기라 master가 죽으면 응답까지 끝난 차감이 사라진 replica가 승격된다. 그 순간부터 같은 수량을 두 번 판다. Sentinel 1대는 감시자 자체가 단일 장애점
  • C 롤백은 오류 콜백이 올 때만 동작한다. 결제창을 닫고 떠난 사용자의 재고를 누가 회수하는지 그림에 없다(만료 워커 부재)
  • D DB는 뒤따라 적는 장부라서 Redis와 어긋나는 것이 정상 상태인데, 어느 쪽이 맞는지 맞춰보는 대사 절차가 없다

전광판이 심판까지 맡으면 빠르지만, 전광판이 꺼졌을 때 누가 맞는지 증명할 수 없어요.

장면 12와의 관계: Redis Lua 차감·Kafka 키 순서·cache-aside 적재는 장면 12에도 그대로 있다. 다른 것은 방향이다. 이 그림은 Redis → Kafka → DB(write-behind)이고, 장면 12는 DB → outbox → Kafka → Redis(read model)다. 장면 12는 이 구조를 버린 게 아니라 ②의 Lua 차감을 Inventory Command 앞의 admission control로 한 단계 안에 넣고, 최종 판정과 이벤트 발행만 DB 트랜잭션 하나로 옮긴 것이다. 짧은 이벤트 판매에는 이 그림이, 초과 판매를 증명해야 하는 상시 재고에는 장면 12가 맞다.

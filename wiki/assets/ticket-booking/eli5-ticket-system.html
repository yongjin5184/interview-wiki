선착순 티켓 예매, 5살에게 설명하기

10만 명이 달려오는데 티켓은 5만 장. 어떻게 안 싸우고 나눠줄까?

장면 1 · 문제

문이 하나인데 10만 명이 달려와요

한꺼번에 밀면 문이 부서지고, 같은 의자에 두 명이 앉아요.

그냥 두면? 문이 무너지고 🧨 한 의자에 두 명 🙅

어른 버전: 평소의 수백 배 스파이크 트래픽이 DB에 직행하면 커넥션 고갈로 전체 장애. 동시 요청이 같은 좌석을 잡는 race condition 발생.
장면 2 · 대기열

번호표를 나눠줘요

놀이공원처럼 줄을 세우고, 내가 몇 번째인지 보여줘요.

한 번에 조금씩만 입장 🚪 나머지는 번호 보며 기다려요

어른 버전: 대기열 서버(가상 대기실). Redis Sorted Set에 (userId, 입장시각)을 넣고 ZRANK로 내 순번 조회. 뒤쪽 서버가 감당할 만큼만 토큰을 발급해 입장시키는 유입 제어(admission control).
장면 3 · 중복 방지

사탕 항아리는 한 손씩만

항아리 지킴이가 한 번에 한 명씩만 사탕을 꺼내게 해요.

꺼낼 때마다 숫자를 하나 줄여요. 0이 되면 끝! 🚫

어른 버전: 지킴이(💂)의 정체가 바로 API 서버(WAS). WAS가 Redis DECR(또는 Lua 스크립트)로 선차감 후, 0 미만이면 즉시 거절. 좌석 지정이면 WAS가 DB에 UPDATE seats SET status='HOLD' WHERE seat_id=? AND status='AVAILABLE' 조건부 갱신 — 영향 행이 0이면 이미 팔린 것. 두 명이 동시에 와도 한 명만 성공. 항아리(Redis)와 공책(DB)은 도구일 뿐, 스스로 움직이지 않는다.
장면 4 · 결제 타임아웃

모래시계가 다 떨어지면 자리 반납

"10분 안에 돈 내세요. 안 내면 다음 사람 줄 거예요."

반납된 의자는 다시 사탕 항아리로 쏙 🔄

어른 버전: 좌석을 HOLD 상태 + 만료시각으로 잡아두고, 결제 완료 시 CONFIRMED로 전이. 만료 처리는 Redis 키 TTL 만료 이벤트나 지연 큐(delay queue)로 트리거하되, 이벤트 유실 대비 만료시각 기준 배치 스캔을 안전망으로 병행. 재고는 다시 +1.
장면 5 · 잃어버리지 않기

공책에 적고, 복사본도 만들어요

지킴이가 넘어져도, 공책만 있으면 누가 예약했는지 다 알아요.

적기 전엔 절대 "예약 완료!"라고 말하지 않아요 ✍️

어른 버전: 확정 예약의 진실 원장(source of truth)은 RDB. WAL + 동기 복제(멀티 AZ)로 커밋된 데이터는 유실 없음. Redis는 속도용 캐시일 뿐, 죽으면 DB 기준으로 재구성. 결제 완료↔예약 확정은 멱등 처리로 이중 결제 방지.
장면 6 · 한눈에 보기

전체 그림

가운데 지킴이(API 서버)가 모든 일을 해요. 항아리와 공책은 스스로 못 움직여요.

어른 버전 매핑: 지킴이 = API 서버(WAS) 여러 대 — Redis와 DB를 호출하는 유일한 주체. 대기열 = 처리율 제한 + 메시지 큐 · 숫자판 = Redis 원자 연산 · 공책 = RDB(WAL, 동기 복제)가 source of truth · 모래시계 반납도 WAS 옆의 워커 프로세스가 수행. Redis↔DB 정합성(차감 후 DB 실패 시 INCR 복원 등)도 WAS의 책임.
장면 7 · Redis 속 들여다보기

SET 하면 안에서 무슨 일이?

이름표를 믹서기에 갈면 서랍 번호가 나오고, 알람은 다른 보드에 따로 붙여요.

값 서랍장과 알람 보드는 분리! 그래서 알람이 있어도 읽기는 똑같이 빨라요

어른 버전: Redis DB 하나 = 거대한 해시테이블(dict). 키를 SipHash로 해싱해 버킷 인덱스를 얻고, dictEntry에 키(SDS 문자열)와 값 포인터를 저장. 10245처럼 작은 숫자 값은 int 인코딩으로 압축 저장. TTL은 값 옆이 아니라 별도의 expires dict에 "키 → 만료 절대시각(unix ms)"으로 저장 — 그래서 GET 성능에 TTL 유무가 영향 없음. 삭제는 ① lazy(접근 시 시각 비교) ② active(주기적으로 expires에서 샘플 추출해 삭제) 두 방식. 이 "샘플링" 때문에 지난 장면의 expired 이벤트 시점이 부정확한 것. 메모리가 꽉 차면 rehash는 점진적(incremental)으로 진행. 디스크에는 RDB 스냅샷/AOF 로그로만 내려간다.
장면 8 · 최종 설계도

전체 시스템 디자인

지금까지 나온 조각을 전부 한 장에 모았어요. 번호 순서대로 따라가면 돼요.

  1. 진입 — 대기열 API가 Redis-Q에 INCR next_number로 번호표 발급
  2. 순서 확인 — 폴링/SSE로 "내 번호 − serving_number" 응답 (WAS 로컬 캐시 1초)
  3. 입장 — 입장 워커가 serving_number를 N씩 올리고 입장 토큰(JWT) 발급
  4. 예매 요청 — 토큰 검증 후 예매 API 입장 (토큰 없으면 거절)
  5. 재고 선차감 — Redis-S에 DECR stock + SET hold:ticket:{id} {userId} NX EX 1800
  6. 원장 기록 — RDB에 HOLD 상태 INSERT. 결제 성공 콜백이 오면 CONFIRMED로 갱신 + hold 키 DEL
  7. 결제 — 외부 PG 호출, 콜백은 멱등 처리 (같은 콜백 두 번 와도 안전)
  8. 자동 취소 — TTL 만료 → expired 이벤트(빠른 경로) + DB 배치 스캔(안전망) → HOLD 취소, 재고 +1
장애 시나리오 요약: WAS 죽음 → 무상태라 아무거나 재시작 · Redis-Q 죽음 → 대기열만 리셋, 예약 데이터 무관 · Redis-S 죽음 → AOF+레플리카로 승격, 최악에도 DB 원장 기준 재구성 · RDB Primary 죽음 → 동기 복제본 승격, 커밋된 예약 유실 없음. 확정 예약의 진실은 항상 RDB — 요구사항 5번(유실 방지)의 근거.
장면 9 · 찜한 자리의 세 가지 결말

쪽지는 찢지 않아요, 도장만 바꿔요

찜(HOLD) 쪽지는 결말이 3개뿐이에요. 어떤 결말이든 쪽지는 공책에 남아요.

찢어버리면(DELETE) 나중에 "내 예약 왜 없어졌어요?"에 답을 못 해요 🙈

어른 버전: HOLD 행은 DELETE가 아니라 상태 전이(UPDATE). 판매 가능 여부는 행의 존재가 아니라 상태값이 결정하므로 EXPIRED 행은 무해하고, 늦은 결제 콜백 판정("존재했지만 만료됨 → 환불")·CS·감사를 위해 반드시 남긴다. 물리 정리는 훗날 날짜 파티션 아카이빙으로.
장면 10 · 버릴 시각 미리 적기

한 번만 계산해서, 두 군데 똑같이 적어요

"30분 뒤"라고 각자 계산하면 어긋나요. 지킴이가 "18:30"이라고 딱 정해서 나눠줘요.

생성일에서 그때그때 계산 ❌ → 만료 시각을 값으로 박제 ⭕

어른 버전: created_at + 30분을 매번 파생 계산하지 않고 hold_expires_at 컬럼에 절대시각으로 저장, Redis에는 같은 값을 EXAT로. 예약별 정책 차이(VIP 60분)·결제 진입 시 연장이 UPDATE 한 줄로 가능하고, "30분" 규칙이 생성 코드 한 곳에만 존재. 워커는 (status, hold_expires_at) 인덱스로 만료 행만 정확히 스캔.
장면 11 · 몇 초쯤 달라도 괜찮아

도장 먼저, 사탕은 나중에

알람은 울렸는데 공책은 아직 그대로인 몇 초. 순서 하나로 사고를 막아요.

실수해도 언제나 "덜 파는 쪽"으로만 기울어요. 한 자리 두 명은 없어요 🛡️

어른 버전: Redis·DB 이중 저장소의 수초 불일치는 의도된 결과적 일관성. 2PC 없이도 안전한 이유는 연산 순서 — 재고 복원(INCR)을 DB 조건부 전이(HOLD→EXPIRED) 성공 후에만 수행. 순서를 뒤집으면 같은 티켓에 HOLD 2개가 생길 수 있어 금지. 최종 판정 권한은 항상 DB의 조건부 UPDATE 한 곳.
장면 12 · 빈자리가 다시 팔리는 길

옛 쪽지는 그대로, 새 쪽지를 새로 써요

만료로 풀린 자리는 "고쳐 쓰는" 게 아니라, 사탕이 항아리로 돌아오고 다음 사람이 새로 찜해요.

"재예약"이란 없어요. 항상 새로운 예약이 태어날 뿐! 👶

어른 버전: 만료 워커가 ① 옛 행을 EXPIRED로 전이 ② INCR stock(좌석제면 seats.status → AVAILABLE). 이후는 최초 판매와 완전히 동일한 경로 — 입장 토큰을 가진 다른 유저의 DECR+SET NX가 성공하고 새 reservations 행이 INSERT된다. 매진으로 대기열까지 닫힌 뒤의 취소표라면 대기열을 재오픈하거나 '취소표 알림' 구독자에게 입장 토큰을 발급하는 정책을 얹는다.
장면 13 · 대안 설계: 컨베이어 벨트

카프카로 줄 세우면? 벨트 위 위치가 곧 순번

모든 주문 편지를 벨트에 올리고, 일꾼이 한 통씩 처리해요. 내 편지 위치 − 처리 중 위치 = 내 순서!

신기하죠? 번호표 카운터 2개와 똑같은 수학이에요. 벨트냐 전광판이냐의 차이! 🔁

어른 버전: 이벤트별 단일 파티션에 모든 예매 요청을 발행 → 컨슈머 1개가 직렬 처리(재고 경합 원천 소멸, 원자 연산조차 불필요). 순번 = 내 메시지 offset − 컨슈머 committed offset — 발행 시 받은 offset을 응답으로 주고, 조회 API가 차이를 계산. 카운터 2개 방식과 수학적으로 동형(next≈producer offset, serving≈committed offset). 장점: 디스크 로그라 요청 유실 없음, 폭주를 벨트가 흡수. 단점: 응답이 비동기 UX(SSE/푸시 필요), 단일 파티션 처리량 한계(수천 TPS — 5만 장엔 충분), 파티션을 늘리면 전역 순서가 깨짐. 2권 4장(분산 메시지 큐) + 6장(스트림 처리) 패턴.

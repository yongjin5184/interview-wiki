# 선착순 티켓 예매 시스템

시각 자료: [ELI5 그림 13장](/wiki/assets/ticket-booking/eli5-ticket-system.html) (브라우저로 열기)

## 1. 요구사항

- 동시 10만 명 접속, 티켓 5만 장
- 중복 예약 금지
- 일정 시간(예: 30분) 내 미결제 시 자동 취소
- 순간 폭주에도 안정 동작
- 사용자가 자신의 대기 순서를 확인 가능
- 장애 시에도 예약 데이터 유실 금지

## 2. 최종 아키텍처

```
사용자 10만 ──①진입──▶ LB ──▶ 대기열 API(WAS) ──▶ Redis-Q (대기열 전용)
   ▲                              │                  next / serving 카운터
   └──②"내 순서?" 폴링·SSE ───────┘                  영속화 없음, 읽기 레플리카
   │
   │        입장 워커 ──③ serving_number += N → 입장 토큰(JWT) 발급
   │
   └──④ 토큰 들고 예매 ──▶ 예매 API(WAS ×N, 무상태) ──⑤ DECR stock
                              │        │              SET hold:{id} {userId} NX EXAT {만료시각}
                              │        └──⑥ HOLD INSERT ─▶ Redis-S (재고·HOLD 전용, AOF+레플리카)
        외부 PG ◀──⑦ 결제 ────┘                             │ expired 이벤트(빠른 경로)
              │                                             ▼
              └─콜백(멱등)─▶ CONFIRMED + hold DEL      만료 워커 ──⑧ HOLD→EXPIRED, 재고 +1
                              ▲                          ▲
                        RDB 예약 원장 ◀──── 배치 스캔(안전망, 30초~1분)
                        Primary + 동기 복제 = source of truth
```

핵심 원칙: **Redis와 DB는 서로 직접 통신하지 않는다.** 둘 다 수동적 저장소이고, 둘을 오가며 정합성을 조율하는 유일한 주체가 무상태 WAS 계층이다.

## 3. 핵심 설계 결정

### 대기열: 메시지 큐가 아니라 카운터 2개

메시지 큐(SQS/Kafka)는 "내가 몇 번째냐"를 임의 조회할 수 없는 단방향 파이프다. 순번 조회 요구사항 때문에 조회 가능한 상태 저장소가 필요하다.

| | Sorted Set (ZADD/ZRANK) | 카운터 2개 (채택) |
|---|---|---|
| 내 순서 | 정확한 순위, O(log N) | 내 번호 − serving_number, O(1) |
| 이탈 처리 | ZREM 가능 | 불가 (순번이 근사값) |
| 비용 | 멤버별 상태 보관 | 숫자 2개가 전부 |

순번은 근사값이면 충분하므로 카운터 2개 채택. 10만 명이 3초 폴링 = 약 33k QPS이나, WAS 로컬 캐시 1초면 Redis에는 초당 수십 건.

### Redis 인스턴스 분리 (Redis-Q / Redis-S)

기능적으로는 한 대로 충분하지만 분리한다:
- **내구성 설정이 다름**: Redis-S(재고·HOLD)는 AOF everysec + 레플리카, Redis-Q(대기열)는 유실 시 재구성 가능하므로 순수 메모리
- **장애 격리**: 대기열 폭주·대량 TTL 만료가 재고 차감 지연으로 전파되지 않게
- **확장 방향이 다름**: 대기열은 읽기 폭주(레플리카), 재고는 원자 쓰기(마스터 집중)
- 주의: 재고 카운터는 단일 핫키라 클러스터 샤딩이 무의미 — 완화는 키 분할(`stock:{eventId}:{section}`)

두 카운터의 본질 차이: `stock`은 자원 원장(오르내림, 보상 필수), 대기열 카운터는 흐름 제어(단조 증가만, 보상 개념 없음). 만료로 재고가 +1 되어도 Redis-Q는 건드리지 않는다 — 입장 워커가 재고를 *읽고* 입장 속도를 정하는 단방향 참조만 존재.

### 중복 예약 방지: 원자 연산 한 줄

```
SET hold:ticket:{ticketId} {userId} NX EX 1800   # NX = 없을 때만 → 한 명만 성공
DECR stock                                        # 0 미만이면 즉시 거절
```

키 설계 원칙: 사용자 식별자는 키가 아니라 **value**에 (키에 넣으면 SCAN 패턴 검색이 필요해지는 안티패턴). 좌석 지정제면 DB 조건부 UPDATE(`WHERE status='AVAILABLE'`)로 대체.

### 만료 시각: 파생 계산 대신 절대시각 박제

`created_at + 30분`을 매번 계산하지 않고, 예매 시점에 WAS가 **한 번만** 계산해 Redis `EXAT`와 DB `hold_expires_at` 컬럼에 같은 절대시각을 기록.
- 예약별 정책 차이(VIP 60분)·결제 진입 시 연장이 UPDATE 한 줄
- 두 시스템의 만료 시점이 단일 진실
- 워커는 `(status, hold_expires_at)` 복합 인덱스로 스캔

### 미결제 처리: DELETE가 아니라 상태 머신

```
HOLD ──결제 성공 콜백──▶ CONFIRMED
 │ └──사용자 취소──▶ CANCELLED (즉시 반납)
 └──30분 경과──▶ EXPIRED (만료 워커가 반납)
```

- HOLD 행은 지우지 않고 EXPIRED로 전이. 판매 가능 여부는 행의 존재가 아니라 상태값이 결정
- 남겨야 하는 이유: 늦은 결제 콜백 판정("존재했지만 만료 → 환불"), CS 대응, 감사. 물리 정리는 훗날 날짜 파티션 아카이빙
- 만료 트리거는 이중화: keyspace notification `expired` 이벤트(빠른 경로, fire-and-forget이라 유실 가능) + DB 배치 스캔 30초~1분(안전망, 최종 책임자). 상세: [Redis 만료의 내부 구조](/wiki/concepts/redis-expiration.md)
- 멱등성: `UPDATE ... SET status='EXPIRED' WHERE status='HOLD'` 조건부 + affected rows=1일 때만 `INCR stock` — 이벤트·배치가 겹쳐도 재고 +2 없음

### 결제 도중 만료 경계

29분 59초에 결제창 진입 → 만료 처리 → 성공 콜백 도착 시나리오:
1. **콜백 시점 조건부 확정 + 자동 환불** (단순): `UPDATE ... WHERE status='HOLD'` 실패하면 PG 환불. 좌석 정합성이 돈보다 우선
2. **결제 진입 시 HOLD→PAYING 전이** (UX 우선): PAYING은 만료 대상 제외, PG 타임아웃으로 별도 관리
실무는 2 + 1을 최후 방어선으로. 콜백은 멱등(같은 콜백 재수신 시 no-op).

### 결과적 일관성: "도장 먼저, 사탕 나중"

Redis 키는 만료됐는데 DB는 수초간 HOLD인 불일치 창은 **의도된 허용**. 안전한 이유는 연산 순서:
1. DB 조건부 전이(HOLD→EXPIRED) 성공 **후에만**
2. 재고 복원(INCR)

검증: 그 창에 새 유저가 오면 재고 미복원이라 못 삼(중복 판매 없음, 판매 지연뿐). 그 창에 결제 콜백이 오면 DB가 아직 HOLD라 확정 성공(경계 결제자에게 관대). 순서를 뒤집으면 같은 티켓에 HOLD 2개 가능 → 금지. 2PC 없이 "불일치가 항상 덜 파는 쪽으로만 기울게" 설계.

### 만료 티켓의 재판매

"재예약" 경로는 없다. 옛 행은 EXPIRED로 종결, 재고 +1 후에는 최초 판매와 동일 경로로 다른 입장자가 **새 HOLD 행**을 만든다. 매진 후 취소표는 대기열 재오픈 또는 취소표 알림 구독자에게 토큰 발급(정책 결정 필요).

## 4. 대안 아키텍처: 카프카 직렬 처리

이벤트별 단일 파티션에 모든 예매 요청 발행 → 컨슈머 1개 직렬 처리(경합 원천 소멸). **순번 = 내 offset − committed offset** — 카운터 2개 방식과 수학적으로 동형.

| | 카운터 방식 (채택) | 카프카 방식 |
|---|---|---|
| 요청 유실 | 대기열 휘발 (재입장) | 디스크 로그, 유실 없음 |
| 응답 | 동기 (즉시 성패) | 비동기 (통지 대기) |
| 확장 | 카운터 무한 | 단일 파티션 수천 TPS 한계 |

유저 영향이 결정적: 비동기화하면 성패 통지가 처리 시점으로 밀려 **매진을 늦게 알고, 좌석 선택형 UX가 불가능**(처리 시점에 그 좌석이 남아있을 보장 없음). 결과 푸시 채널(SSE)과 요청 ID dedup 필수. 대신 접수는 절대 실패·유실 없음. → 좌석 지정 티켓팅은 대기열+동기, 선착순 쿠폰·응모는 카프카+비동기가 정석.

## 5. 면접 한 줄 정리 모음

- **전체**: "Redis는 속도용 보조 카운터, RDB는 진실의 원장, 둘의 일관성을 조율하는 오케스트레이터가 무상태 WAS 계층입니다."
- **대기열**: "메시지 큐는 순번 조회가 불가능한 파이프라 쓰지 않고, 발급 번호와 처리 번호 카운터 2개의 차이로 O(1) 조회합니다."
- **TTL**: "Redis TTL은 값의 속성이 아니라 별도 expires 해시테이블의 절대시각이고, 삭제는 lazy+샘플링이라 만료 시점이 정확히 보장되지 않는 것까지가 한 세트입니다."
- **만료 처리**: "키 삭제는 Redis가 알아서, 트리거가 필요한 건 재고 복원과 원장 갱신입니다. 이벤트는 빠른 경로, 배치 스캔이 안전망, 조건부 UPDATE로 멱등하게."
- **일관성**: "수초의 불일치 창은 의도된 결과적 일관성이고, 재고 복원을 DB 전이 성공 이후로 배치해 불일치가 항상 '판매 지연'이라는 무해한 방향으로만 나타납니다."
- **미결제**: "HOLD 행은 DELETE가 아니라 상태 전이로 처리합니다. 늦은 콜백 판정·CS·감사를 위해 남기고, 물리 정리는 파티션 아카이빙으로."

## 6. 남은 연습 거리

- 규모 추정을 숫자로 직접 계산 (QPS, 저장량, 리틀의 법칙)
- 좌석 지정제 변형 (좌석맵 캐싱, 구역별 핫키 분할)
- 멀티 리전 시나리오
- 예상 꼬리 질문 세트를 [질문 은행](/wiki/questions/)으로 분리
